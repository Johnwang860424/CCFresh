## Why

顧客可能因重複點擊、網路延遲或不確定前一次是否成功而重複送出訂單，造成重複扣庫存與後續人工確認成本。建立訂單前以姓名及聯絡電話共同辨識疑似重複訂單，可在不阻止合理再次購買的前提下提醒顧客確認。

## What Changes

- 新訂單的姓名不得包含任何空白字元；結帳介面與建立訂單 API 都會拒絕含空格、Tab 或換行的姓名，並顯示「姓名不可包含空白」。
- 建立訂單前，使用正規化後的聯絡電話與未經 trim 的姓名原值查詢既有訂單；兩者皆完全相同才視為疑似重複。
- 疑似重複時不立即寫入訂單，回傳可辨識的 API 結果，並在結帳介面顯示「系統偵測到您可能已有訂單。請確認是否為重複下單」。
- 顧客可返回檢查訂單，或明確確認仍要送出；確認後沿用既有伺服器端驗證、定價、庫存扣減及快取更新流程建立訂單。
- 找不到姓名與電話皆相同的既有訂單時，維持一次送出即直接建立訂單的流程。

## Capabilities

### New Capabilities
- `duplicate-order-warning`: 定義建立訂單前的姓名與電話重複偵測、API 回應，以及顧客確認後繼續下單的互動。

### Modified Capabilities

無。

## Impact

- `app/domain/order.ts` 與共用型別：接受並驗證顧客是否已明確確認疑似重複訂單的欄位。
- `app/lib/validation.ts`：提供前後端共用的姓名不可含空白驗證。
- `app/lib/orders.ts`：以參數化 SQL 查詢姓名與正規化電話相同的既有訂單，並控制提醒或繼續寫入。
- `app/api/orders/route.ts`：新增疑似重複訂單的可辨識回應狀態與內容。
- `components/CheckoutForm.tsx`：顯示確認提示，支援返回檢查或確認送出，並避免重複請求。
- 單元測試與 API／UI 關鍵流程測試需涵蓋未重複、疑似重複及確認後送出的情境；不需新增資料表或第三方相依套件。
