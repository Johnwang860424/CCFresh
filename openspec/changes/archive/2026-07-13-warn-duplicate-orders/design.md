## Context

目前 `POST /api/orders` 會先由 `prepareOrder()` 正規化姓名與電話、依最新商品資料驗證及計價，再由 `createOrder()` 解析取貨點並直接寫入訂單、品項與庫存異動。前端 `CheckoutForm` 對非 2xx 回應一律顯示一般送出錯誤，尚無可暫停送出並要求顧客確認的結果類型。

本變更橫跨共用請求型別、訂單資料層、API 狀態碼與結帳互動。重複判斷僅使用既有 `orders` 資料，不改 DB schema；同姓名同電話可能是合理的再次購買，因此偵測結果必須是可覆寫的提醒，而不是永久禁止。

## Goals / Non-Goals

**Goals:**

- 使用前後端共用規則拒絕姓名中的任何空白字元，並在重複查詢前回傳一致錯誤。
- 在任何訂單、品項或庫存寫入前，以姓名及聯絡電話共同偵測疑似重複訂單。
- 讓 API 以穩定的 machine-readable code 區分疑似重複與一般驗證／伺服器錯誤。
- 讓顧客看見指定警告文字後選擇返回檢查，或明確確認仍要建立訂單。
- 確認送出時仍完整執行現有的伺服器驗證、權威計價、防超賣及快取更新流程。

**Non-Goals:**

- 不自動取消、合併或刪除既有訂單。
- 不比較購物內容、取貨點、配送地址、時間區間或訂單狀態。
- 不以模糊比對推測姓名別名，也不建立姓名／電話唯一限制。
- 不改動電話查詢既有訂單功能或 DB schema。

## Decisions

### 1. 先完成既有輸入正規化，再查詢所有歷史訂單

`prepareOrder()` 先對原始 `customerName` 執行共用 `isValidCustomerName()`；空字串沿用必填錯誤，任何位置出現 `\\s` 空白則回傳「姓名不可包含空白」，不先 trim 來掩蓋錯誤。通過後保留姓名原值，電話則經 `normalizePhone()` 處理。

資料層以參數化 SQL 直接比對 `customer_name = customerName`，不得使用 `btrim`；電話仍以既有相容方式移除資料庫值中的空白與連字號後比對。只有兩個條件同時相等才命中。這表示歷史姓名若含首尾空白，不會與新的無空白姓名命中。

比對涵蓋所有既有訂單，因需求未指定時間窗或狀態，且目前 schema 資訊沒有可依賴的取消狀態。替代方案是只檢查近期訂單，但會引入未定義的業務門檻並漏掉較早的同名同電話訂單。

### 2. 使用既有建立訂單 endpoint 的兩階段確認契約

第一次 `POST /api/orders` 未帶 `confirmDuplicate: true` 時執行重複查詢：

- 未命中：維持 `201` 與既有成功 payload。
- 命中：回傳 `409`，body 為 `{ code: "DUPLICATE_ORDER", error: "系統偵測到您可能已有訂單。請確認是否為重複下單" }`，且不進行任何寫入或庫存異動。

顧客確認後，前端以相同訂單 payload 加上 `confirmDuplicate: true` 再送一次。伺服器只把布林值 `true` 視為明確確認，略過重複提醒後繼續既有流程；它不略過其他驗證，也不信任前端價格。使用同一 endpoint 可避免增加一個只供前端呼叫的檢查 API，並確保直接呼叫建立 API 的客戶端也會受到保護。

### 3. 結帳介面以確認對話框處理重複結果

`CheckoutForm` 只在 HTTP 409 且 `code === "DUPLICATE_ORDER"` 時顯示確認介面與指定警告文字。介面提供「返回確認」與「仍要送出」兩個明確動作；返回時不清空表單或購物車，確認時重送同一份已驗證的表單與購物車快照並附上確認旗標。

第一次請求、等待顧客選擇及確認請求期間都要防止重複提交。一般 400/5xx 繼續走現有錯誤顯示，成功後才儲存訂購人資料並開啟成功畫面。

### 4. 將純資料形狀與分支行為保持可測試

共用 `PlaceOrderRequest` 增加可選的 `confirmDuplicate`，`prepareOrder()` 僅接受嚴格布林值並輸出是否確認，避免 truthy 字串繞過提醒。`app/lib/validation.ts` 提供不含 server-only 依賴的 `isValidCustomerName()`，供 `CheckoutForm` 與 `prepareOrder()` 使用；重複身分 helper 不再 trim 姓名，只正規化電話。重複查詢維持在 server-only 資料層，route 與 SQL adapter 保持精簡。

## Risks / Trade-offs

- [所有歷史訂單都會參與比對，回購顧客也會收到提醒] → 提醒允許明確繼續送出，且不揭露既有訂單內容。
- [沒有姓名／電話索引資訊時，正規化查詢可能隨訂單量成長而變慢] → 先以 `EXISTS ... LIMIT 1` 避免載入資料；若實際監測顯示需要，再由 DB 管理端評估正規化欄位或 expression index。
- [兩個幾乎同時抵達且資料相同的首次請求可能都在對方寫入前完成查詢] → 此功能定位為防呆提醒而非唯一性保證；既有庫存原子扣減仍防止超賣。若未來要求強一致去重，需新增可鎖定的去重鍵或冪等鍵。
- [前端只靠警告文字辨識會受文案變更影響] → 使用穩定的 `DUPLICATE_ORDER` code 分支，文字只供顯示。
- [確認請求期間商品或庫存可能改變] → 每次請求都重新執行 `prepareOrder()` 與現有 DB 防超賣流程，不沿用第一次請求的價格或庫存判斷。
- [少數合法姓名可能慣用空格分隔] → 依本次明確業務規則一律拒絕，介面顯示具體錯誤讓顧客改為無空白姓名。

## Migration Plan

1. 先部署可接受 `confirmDuplicate` 並回傳 `DUPLICATE_ORDER` 的伺服器與共用型別變更，再同步部署能處理該結果的前端。
2. 不需資料遷移；既有含空白或連字號的電話以查詢時正規化相容。
3. 驗證姓名空白的前後端拒絕、姓名精確比對、未重複直接成功、重複不寫入、返回確認不送出、確認後成功，以及確認時庫存不足等流程。
4. 若需回滾，移除重複查詢與前端確認分支即可；新增的可選請求欄位不影響既有資料。

## Open Questions

無；目前依需求將所有既有訂單納入判斷，未來如需限定「近期」或排除特定狀態，應另行定義業務規則。
